## 구조
- `app/api/board/route.ts`: 실제 조회 및 공개 fixture 재생
- `lib/core.ts`: 정규화·검증·날짜·오류 분류·변화 계산
- `lib/storage.ts`: live와 replay 공통 D1 저장 함수
- `db/schema.ts`, `drizzle/`: 복합 기본키 및 마이그레이션
- `data/t04/`: 수정하지 않은 공개 기준·fixture. 17개 SHA-256 대조 완료
- `app/page.tsx`: 정보판, 장애·복구 검증, 확인 방법

`scope + signal + date` 기본키에 atomic UPSERT를 사용합니다. 실패는 상태만 변경하고 읽기 테이블을 건드리지 않습니다. 합성 시험은 무작위 세션 scope에서 진행하여 실제 live 기록과 분리합니다. 이 세션은 인증이나 개인정보가 아닙니다. 실제 저장 실패는 외부 데이터 오류로 처리하지 않습니다.

## 실행
기존 잠금파일과 pnpm 사용. 의존성 설치 후:
1. `python scripts/source-snapshot.py`
2. `pnpm build`
3. 생성된 Worker 설정으로 D1 마이그레이션 적용 후 개발/Worker 실행.

Sites는 배포 시 D1 바인딩과 저장된 마이그레이션을 적용합니다. `.openai/hosting.json`의 `d1`은 `DB`입니다.

## 확인 방법 · 4줄
① 위치: 정보판 및 장애·복구 검증 화면.
② 행동(3단계): 실제 기온 조회 → 전체 합성 검증·105 응답 지연 후 다시 시도 → 다음 실제 KST 날짜에 다시 실제 조회.
③ 통과 모습: 값·단위·출처·출처 시각·조회 시각·시간대 표시, 합성 8/8, 실패 105/1건/stale, 복구 120/2건/fresh/none, 실제 두 기록의 변화 재계산 일치.
④ 실패 모습: 오류 원인·다음 행동·오래된 값과 다시 시도 버튼, 기존 정상값 보존. 저장 장애는 별도 안내.

## 실제 날짜와 영수증 한계
합성 D1/D2는 실제 이틀 증거가 아닙니다. 첫날 실제 조회 후 다른 실제 KST 날짜에 한 번 더 조회해야 합니다. 플랫폼에서 봉인하는 canonical kind `t04_day` 영수증은 이 앱이 발급하거나 위조하지 않습니다. ALEPH 제출 과정에서 정확히 2건을 남기고 앱 기록과 대조해야 합니다. 플랫폼 영수증 발급 API는 제공받지 않아 자동 연결하지 않았습니다.

## AI와 학생 판단 · 제출 전 학생 확인 필요
AI에게 맡긴 일: 구현, 공개 fixture 분석, 실행 검증.
학생이 직접 판단한 일: 실제 학생이 결정한 내용으로 제출 전에 작성.
AI 제안을 따르지 않은 일: 실제 사례 또는 없었던 이유로 제출 전에 작성.
AI가 학생의 결정을 지어내지 않습니다.

## 변화 규칙
저장된 최신 두 조회 날짜의 같은 신호·같은 단위 값을 뺍니다. 최신값 - 이전값을 부호 있는 변화값으로 표시하고 절대 변화도 계산합니다. 날짜 간격은 화면에 명시합니다. 단위가 다르면 비교하지 않습니다. 합성 105 → 120은 +15 pt.

## 현재 범위
공개 조회와 새 날짜 기록, 실제 응답 원문 보존, 다섯 오류 및 재시도. 자동 정기 조회나 개인 데이터는 없습니다. 수치예보 출처: https://open-meteo.com/en/docs · CC BY 4.0.
## 2026-10-02 공개 원천 조회 경로

방문자 브라우저가 동일한 Open-Meteo 공개 URL을 조회하고 원자료를 저장 API로 전달한다. 서버는 좌표·단위·값·출처 시각(현재 기준 2시간 이내)을 검증하고 서버의 실제 조회 시각으로 KST 일별 날짜를 정한다. 브라우저 CORS/네트워크 오류 때만 기존 서버 조회를 한 번 사용한다. HTTP 429는 자동 반복하지 않고 기존 정상 기록과 오류 상태를 보존한다.

이 경로는 배포 서버의 공유 출구 IP에 걸린 호출 제한으로 모든 방문자의 조회가 막히는 문제를 줄인다. 전달된 브라우저 원자료의 형식을 검증하지만 원천 서명이나 플랫폼 봉인 영수증을 대신하지 않는다. 플랫폼 영수증과 실제 원자료·저장값·화면값을 별도로 대조해야 한다.
